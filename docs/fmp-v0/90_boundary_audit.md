Status: **preliminary**. Phase 1 has not started. This document records findings
from the initial read so they are not lost to context compaction. Every claim
here is labelled with its basis and confidence; nothing is `verified`.

## 2. Findings

### F-01 — The library covers three encoders, not four

- Evidence: `deps/xirasm-lib/src/xirasm_backend.zig:3-5`
  exports `x86`, `riscv`, `spirv`.
- Repository tree under `deps/xirasm-lib/src/` contains `x86_encoder/`,
  `riscv_encoder/`, `spirv_encoder/`; there is no `aarch64_encoder/`.
- Interpretation: AArch64 is **not** available as a callable library backend.
- Confidence: high (direct file listing).

### F-02 — The library excludes exactly the FMP surface

- Evidence: `deps/xirasm-lib/README.md:12-19` lists as out of scope: assembler
  symbol tables and labels, pseudo directives and frontend source control,
  runtime executable-page allocation, C ABI shellcode runners, Meta VM/frontend
  language behavior, object/linker ownership.
- Interpretation: layout, symbols, fixups, and object formats are frontend
  responsibilities, so a "reuse the library" route would still require building
  the entire FMP layout/fixup layer ourselves.
- Confidence: high (documented scope + matching module absence).

### F-03 — RISC-V encoding entry point is mnemonic-driven

- Evidence: `deps/xirasm-lib/src/riscv_encoder/api.zig:24-57` exposes
  `encode(EncodeRequest)`, `encodeRaw(...)`, `encodeMnemonic(mnemonic, xlen,
  operands)`; `types.zig` defines
  `EncodeRequest{ mnemonic, xlen, operands }`,
  `Operand = union(enum){ reg: u5, imm: i64 }`.
- `api.zig:39` resolves the spec via
  `tables.instructionByMnemonicForXLen(request.mnemonic, request.xlen)`.
- `types.zig` exposes `InstructionSpec{ match: u32, mask: u32, format, semantic,
  bit_width, fields }`, so a form identity *could* be derived from `match/mask`.
- Interpretation: the public API selects a form internally from a mnemonic. A
  form-direct adapter would need access to `InstructionSpec` plus a stable
  identity derived from `match/mask`, which is not exposed as an id.
- Confidence: high for the signatures; medium for whether a caller can pin a spec.

### F-04 — Two encode modes with different semantics

- Evidence: `api.zig:24-30` (`encode` → `.semantic`, `encodeRaw` → `.raw`) and
  `encode.zig:4,8` dispatch to separate implementations.
- Interpretation: "semantic" mode is the natural place for alias or
  pseudo-behavior; the exact difference must be traced in `encode.zig`, not
  inferred from the names.
- Confidence: medium — the distinction is observable, its effects are not yet read.

### F-05 — x86 exposes an explicit branch-relaxation hint

- Evidence: `deps/xirasm-lib/src/x86_encoder/api.zig:78`
  `branch_relaxation_hint: ?BranchRelaxationDecision = null`, where
  `BranchRelaxationDecision = { rel8, near }` (`api.zig:164-171`), plus a
  `withBranchRelaxationHint`-style setter at `api.zig:153` and a use at
  `api.zig:331`.
- Interpretation: relaxation can be *constrained* by a caller, but the default
  (`null`) leaves the decision inside the encoder. For FMP that default is
  unacceptable; the audit must prove the hint is honored on every path, including
  the assembler-style `encodeBuiltinUnits(allocator, mnemonic, operand_refs,
  context)` entry point.
- Confidence: medium — signature and one use site seen, behavior unverified.

### F-06 — AArch64 encoding exists as generated meta-DSL, not as an API

- Evidence: `include/arm/a64/generated/latest/source-bodies.inc` ~6.9 MB,
  `source-dispatch.inc` ~5.6 MB, `entry.inc` ~1.3 MB; generated by
  `tools/arm64/generate_a64.py` and rule files under `tools/arm64/rules/`.
- Frontend includes `src/frontend/meta_function.zig`, `meta_control_flow.zig`,
  `macro.zig`.
- Interpretation: AArch64 encoding is executed by XirAsm's own Meta VM at assembly
  time. Using it would import a language runtime into the materializer, which
  INV-06 forbids. It remains usable as *knowledge* (the generated tables encode
  the ISA rules) but not as a linked component.
- Confidence: medium — file sizes and module names verified; runtime behavior
  not yet executed.

### F-07 — The repository ships ISA test matrices usable as vectors

- Evidence: `tests/isa/x86/*.asm` (branch boundary, REX, addressing, fixup
  matrices), `tests/isa/riscv/rv64-*.asm`, `tests/isa/arm/check_a64_*.py`.
- Interpretation: these are excellent *prompt lists* for what to test, but they
  are produced by the system under review, so they are not independent oracles.
- Confidence: high.

## 3. Consequences for the contract

| Finding | Consequence |
|---|---|
| F-01 | AArch64 needs an independent knowledge source (OD-07). |
| F-02 | Layout/symbol/fixup design is ours regardless of route. |
| F-03, F-04 | A form-direct API does not exist; Route A would need a fork, not an adapter. |
| F-05 | x86 encoding requires proving the hint path, or not using that entry point. |
| F-06 | The Meta VM is a hard boundary: knowledge yes, runtime no. |
| F-07 | Test ideas yes, oracle no. |

## 4. Phase 1 work queue

1. Trace `x86_encoder/size.zig` and `encode.zig`: where `calcsize` and
   relaxation decisions are made; can `branch_relaxation_hint` be made mandatory
   without a fork?
2. Trace `x86_encoder/match.zig`: does the caller supply a matched form, or does
   the library select one?
3. Trace `riscv_encoder/tables.zig`: how multiple specs for one mnemonic are
   ordered and selected; whether `encodeRaw` avoids alias handling.
4. Confirm whether compressed RISC-V forms are reachable only by explicit `c.*`
   mnemonics or also by semantic rewriting.
5. Confirm that no AArch64 Zig encoder exists anywhere in the tree.
6. LLVM: record the exact release used as oracle, and the precise boundary of
   `MCCodeEmitter` vs `MCAssembler` relaxation.
7. Produce `01_reuse_matrix.md` with A/B/C/D classification and evidence rows.
