| OD-01 | Does the plan carry expected bytes? | A: form + operands + choices only; B: plus optional expected bytes/hash; C: full byte template + explicit patch fields | One vertical slice per ISA built under A and B; measure plan size, verifiability, and whether B catches real definition drift | AC-04, AC-07 | **accepted 2026-11-04: variant B, hash only.** `EXP-0002` measured 92 B per instruction (+21.4 % over A). A misses a same-length encoder defect (`48 89 d8` → `49 89 d8`, both 3 B, both legal); B catches it via `E-BYTE-001`; C is 64 % smaller but has no operand to range-check (`+2147483648` becomes `-2147483648`) and no form to look up. Raw expected bytes stay forbidden — a hash cannot be emitted, so it cannot become the decision. Digest is a check, never an input; its derivation source must be recorded. |
| OD-02 | When is a fixup applied vs. recorded? | Resolve in place when the target is local; always emit a record for unresolved; always emit for cross-section | The three AC-05 cases plus one external-symbol case; measure whether "record" loses information | AC-05 | **accepted 2026-11-04: two modes, one effect each.** `resolve_in_place` computes, range-checks and writes, and emits no record; `emit_relocation` zeroes the covered bits and emits one RELA-shaped record, and never computes a value. `reject_if_unresolved` was removed because it was byte-identical to `resolve_in_place` in both target states. The mode is a function of the plan, never of symbol liveness, or the same plan would emit different bytes when a symbol becomes defined. "Resolved bytes plus a record" is excluded: it needs two fixups on the same bits (`E-FIXUP-006`) and leaves authority ambiguous. `EXP-0002` §6 shows the record loses nothing: site, bit range, target, addend, PC rule, transform, range and pair relation are all present. See `03_fixup_model.md` §5, §8. |
| OD-03 | Which output level does v0 ship? | Level 0 only; Level 0 + Level 1; Level 2 | Whether any AC-05 case is inexpressible without symbol/relocation table structure | AC-03 | **accepted 2026-11-04: Level 0 mandatory, Level 1 optional and deferred, Level 2 out.** `EXP-0002` §6 expressed all three AC-05 shapes as Level 0 records and compared them against `llvm-readobj`. No case needs a symbol or relocation table to be expressed; Level 1 adds serialization, and for RV64 it *adds* work, because `R_RISCV_PCREL_LO12_I` names the `auipc` site and a Level 1 emitter must synthesize a local symbol for it. Consistent with ADR-0003, which is not superseded. |
| OD-04 | How is `form_id` made stable? | Namespace + mnemonic + variant + encoding family; definition-assigned opaque id + digest; match/mask pattern from the definition | Two definition revisions with a renamed form; confirm the id survives or fails loudly | AC-08, Q2 | **accepted 2026-11-04: structured name, exact lookup, loud failure.** The form is `family:mnemonic/variant[/encoding-family]`; an id absent from the pinned definition is `E-FORM-001`, and a definition revision that renames a form changes the digest, so the old plan stops at `E-DEF-001` first. Silent survival across a rename is not required and not offered: no alias table, no deprecated-name window. Two variants that differ only in direction (`rm-r64`/`r64-rm`) or in an implicit register (`rax-imm32`/`rm64-imm32`) are distinct ids; a variant that exists only to encode a value-driven choice ("fits in 8 bits") violates `INV-02`. Opaque ids are rejected because they can be reassigned with the plan none the wiser; `match`/`mask` is rejected by the counterexample already recorded (rv32/rv64 `slli` share `0x00001013`, differ in field width). Confirmation: `N01` (absent or renamed id → `E-FORM-001`, no near-match) and `EXP-R5` (the digest gate fires first when the revision is honest). See `01_contract.md` §7. |
| OD-05 | How are unknown fields and extensions handled? | Reject all; allow `x_*` namespaced fields; version-gated extension objects | A plan written by a newer planner read by an older materializer | AC-10, Q10 | open |
| OD-06 | What does the definition digest cover, and how are upgrades handled? | Hash the generated tables; hash the normalized rule source; hash both; hash plus explicit compatibility classes | A one-byte rule change (immediate range) and a comment-only change; confirm the first breaks and the second does not | N10, EXP-R5 | **accepted 2026-11-04: the digest covers the whole definition document, in canonical form.** The definition is data-only JSON (`07_definition_format.md`), so there is nothing to exclude and no second source of truth: `digest = sha256(canonical_json(document))`, with canonical JSON as §12 defines it. `EXP-0004` §4 measured both halves — changing `imm8`'s range from 8 to 9 bits moves the digest (`c6bfa9…` → `505a42…`), while re-serialising the same document with keys in reverse order leaves it identical. A comment-only change is unrepresentable rather than ignored: JSON has no comments and canonicalization would drop the whitespace. Upgrade policy follows from that: a plan is bound to `namespace + version + digest`, a rule change is a new `version`, and an old plan reading a new table stops at `E-DEF-001`. |
| OD-07 | Where does AArch64 encoding knowledge come from? | Re-derive from the ISA manual; extract from XirAsm's generated meta-DSL; extract from LLVM TableGen; combination | A slice with `add`/`b.cond`/`adrp` producing oracle-matching bytes from own tables | AC-03, AC-05 | **accepted 2026-11-04: the Arm Architecture Machine Readable Specification, 2026-06.** The A64 facts come from the MRS, not from XirAsm's 40.9 MB Meta program (`F-12`) and not from LLVM TableGen; LLVM stays an oracle. The two `NOTICE` files in the snapshot scope the licences: the source inventory and encoding mappings are under a three-clause BSD notice ("Copyright 2010-2026 Arm Limited or its affiliates"), while MPL-2.0 covers only the enumerated operand-translation scripts adapted from dynasm-rs. We generate our own table from the data, copy no MPL-2.0 file, and ship the Arm notice with `definitions/aarch64/`. ADR-0006 closes the residual licence risk for the OPENSOURCE packaging: `EXP-0007` read its `_meta.license` and `docs/notice.html` (BSD-3-Clause) and pinned the archive by hash. The table is now frozen: `definitions/aarch64/0.1.0.json` holds the four forms generated by `EXP-0008`, and `A64-P1`/`P2` (unscaled half)/`P5`/`P6` match `llvm-mc`. `0.2.0` adds `aarch64:add/x64-imm12-lsl12`, which carries the `sh=1` half of `A64-P2` without a new format feature (ADR-0011: the form fixes `sh`, the slot stays `imm12` field content). `0.3.0` adds `aarch64:b.cond/imm19`, where the 4-bit condition is an operand (`aarch64.cond`/`cond4`) and not sixteen forms (ADR-0012, `EC-29`), so `A64-P4` passes. `A64-P3`/`P7`/`P8` stay absent, so naming them is `E-FORM-001`. | OD-09 | What integer/address model does the plan use? | i64 everywhere with explicit width checks; per-field typed integers; arbitrary precision | A negative offset, a `u64` address, and a 33-bit intermediate in `hi20` computation | AC-02 | **accepted 2026-11-04: exact integers with declared domains and one check per value.** Domains: addresses `u64` bounded by `address_width`; offsets/sizes `u64`; addends `i64`; operand immediates per the form's `{signed, bits, align_bits}`; computed fixups per `range_constraint`. Arithmetic is exact signed (≥128-bit headroom), never `address_width` bits and never the host word size; a negative displacement is `-4`, not a reinterpreted pattern. `align_bits` is checked before `value_transform`, `signed`/`bits` after it, and intermediates are never checked — otherwise `pcrel_hi20`'s `+0x800` would reject legal plans. Measured counterexamples in `01_contract.md` §3.2: `0xFFFF_FFFF_FFFF_F000` vs `i64::MAX`; `add rax, 2147483648` (`EXP-0002` W3); `hi20` at `0x7FFF_F800`, where 32-bit wrap yields `-524288` (legal, wrong) while exact arithmetic yields `524288` (out of range, rejected). |
| OD-10 | What is v0's minimal supported feature surface? | Only the EC entries required by the three slices; all EC entries with a proof; defer x86 VEX/EVEX and RISC-V atomics | Slice construction; each deferred feature needs a rejection test | AC-09, AC-10 | **accepted 2026-11-04: only the forms the slices use.** The definition table is the feature surface — an absent variant is `E-FORM-001`, never a flag, a fallback or a partial form. x86-64 surface fixed: 7 forms covering `EC-01`, `EC-03`, `EC-04`, `EC-27` (`02_encoding_choices.md`, "v0 surface"). `EC-05`, `EC-09` (VEX/EVEX) and `EC-10` are out. AArch64 and RV64 surfaces are fixed with their slices under the same rule; their `EC` rows stay `draft` where marked. **Amended 2026-11-05 (`ADR-0030`): `X86-P9` lifts the VEX/EVEX deferral.** The x86-64 surface is now 25 forms: the original 7 plus the RIP-relative (`0.2.0`, `ADR-0027`), base+displacement (`0.3.0`, `ADR-0028`), prefix (`0.4.0`, `ADR-0029`) and encoding-family (`0.5.0`, `ADR-0030`) rows. `EC-09` is frozen; `EC-05` and `EC-10` stay out, as do RISC-V atomics. `0.5.0` declares `avx`/`avx512f`/`avx512vl` because its EVEX row is `EVEX.128`, and a plan naming that table must declare the same set (`E-TARGET-001`). |
| OD-11 | Where is a byte-affecting encoding decision carried? | A: a fine-grained `form_id` absorbs it; B: coarse `form_id` + explicit `encoding_choices` enums; C: mixed per decision | Count the `EC` rows that leave a residual choice after naming a form; find a case two honest implementers of the same `form_id` and operands must encode differently | OD-04, AC-04, N01 | **accepted 2026-11-04: A. `encoding_choices` removed.** The registry's own Owner column assigned every `EC` row to `form_id`, a typed operand or a fixup field, which made the field always empty and `N01`/`E-CHOICE-*` unreachable. Measured: `89`/`8B`, `83`/`81`, `05`/`81` and `EB`/`E9` are distinct ISA opcode-table rows, not residual choices; `40 89 d8` (redundant prefix) is the one unsupported variation and is pinned by a definition rule. `EC-*` is now a registry of decision sites with a closed carrier set. See ADR-0004; `E-CHOICE-001/002/003` retired. |
| OD-12 | Where does RV64 encoding knowledge come from? | riscv-opcodes field ranges; the UDB resolved spec; the ISA manual prose; LLVM TableGen | A slice with `beq`/`jal`/`c.addi` producing oracle-matching bytes from own tables | AC-03, AC-04, AC-05 | **accepted 2026-11-04: the UDB resolved spec, pinned by archive hash.** `EXP-0009` measured that riscv-opcodes states field ranges (`bimm12hi 31..25`, `bimm12lo 11..7`) but not the value-bit scatter, which is exactly what `RV-P4`/`P5`/`P6` must pin; the UDB node states it (`location: "31|7|30-25|11-8"`, `left_shift: 1`), and fourteen vectors encoded from `location` match `llvm-mc` byte for byte. The pinned drop is `resolved_spec.tar.gz` (`sha256:be184986…`, `2694443` B); riscv-opcodes stays the upstream cross-check and `llvm-mc` the oracle. `not: 0` on `c.addi` was not expressible in `fmp-def/0.1`, so `RV-P7` waited for a format decision; ADR-0009 supplied it (the slot's `excluded` list), and both documents are now generated from this source (`EXP-0012`). See ADR-0007; `EXP-0009`; `definitions/rv64/NOTICE`. |
| OD-13 | How is a memory operand represented? | A: one composite `mem` payload per ISA; B: one operand per encoded field, addressing form in the `form_id`; C: one `form_id` per mnemonic with the addressing form chosen from the operand values | A `ld`/`sd` slice and an x86 displacement-width case, measured: can one operand carry a 5-bit base and a 12-bit offset without ambiguity, and does the encoding form change with an operand's value? | AC-03, AC-04, `X86-P4`–`P6`, `A64-P3`, `RV-P3` | **accepted 2026-11-04: B, one operand per field.** `EXP-0011` measured three cases. `ld a0, 8(a1)` spans `xs1`/`imm`/`xd` with three ranges, and a fixup covering `imm` owns a different field than `base`. On x86 the same mnemonic is 4 bytes with a disp8 and 7 with a disp32 (`48 8b 41 08` vs `48 8b 81 00 10 00 00`), and `[rbp]` forces a disp8 (`48 8b 45 00`), so C would choose an encoding form from an operand's value (`INV-02`). AArch64's `ldr x0, [x1, #16]` encodes `imm12 = 2`, so a byte-displacement payload would also need a scaling rule; `A64-P3` pins the answer: `disp` is field content, so the plan states `2` on the `imm12` row and `16` on the `ldur` row, and the four addressing kinds are four forms (`ADR-0013`, `EXP-0015`). §8.1 keeps its four shapes and a composite object is `E-OPERAND-003`, now pinned by `N15`. See ADR-0008; `EXP-0011`. |
| OD-14 | How does a form reject a value that is inside its field's range but illegal? | A: a named predicate (`non_zero: true`); B: a closed list of excluded exact values on the slot; C: a plan-level rule by role or mnemonic | A measured instruction whose illegal value is in range, and a check that no existing code (`E-RANGE-001`/`002`) can reject it | `RV-P7`, `EC-19`, `EC-20` | **accepted 2026-11-04: B, a closed `excluded` list.** `EXP-0012` measured `c.addi a0, 0` → `01 05` and `c.addi x0, 1` → `05 00`, which `llvm-objdump` prints as `c.addi a0, 0x0` and `c.nop 0x1`: zero is inside `[-32, 31]`, so `E-RANGE-001` cannot fire, and the encoding is a HINT rather than the addition. The UDB source states `not: 0` on `imm` and `xd`, and the same construct covers Zilsd's odd-register list. A boolean predicate would be replaced by a list on the second constraint (`INV-06`); a role-level rule would reject `addi ..., 0`, which is legal. Rejection is `E-RANGE-004`; `c.addi` enters as `rv64/0.2.0.json` because the document's extension set moves with it. See ADR-0009; `EXP-0012`; fixtures `RV-P7`, `N16a`, `N16b`. |
| OD-15 | How does a `hi`/`lo` pair express RISC-V's "the low half names the high half"? | A: `pcrel_begin` on the `lo` plus a `hi` offset smuggled through `target`; B: a `pcrel_hi` rule meaning "`P` is the paired `hi`'s site", plus a `pcrel_lo12` transform; C: keep the group 1:1 and require one `auipc` per reference | A normative statement of the pair relation, and a measured case where the rule and the transform differ from their absolute counterparts | `RV-P8`, `AC-05` | **accepted 2026-11-04: B.** The psABI (`riscv-elf.adoc:1578-1605`, `:1184`, `:1186`, read at `v2.0-rc0`) states that the low relocation's symbol is "a label pointing to an instruction in the same section with a high-part relocation entry that points to the target symbol", that its value is `symbol_address - hi20_reloc_offset` i.e. the low bits of the *paired* high-part value, that "the addend must be 0", and that one `hi` may serve "one or more" `lo`s that are "not necessarily sequential". A is rejected because `pcrel_begin` measures from the `lo`'s own site, so an `auipc` at 0 and an `addi` at 4 pointing at a symbol at 0 disagree by 4; C is rejected because it makes the plan express the linker's deduplication job and changes bytes to satisfy a validator. `lo12_s` stays undefined: the `_i`/`_s` suffix names the instruction form, which `form_id` already carries (`OD-11`), so an S-type low half is `pcrel_lo12` with an S-type descriptor. See ADR-0010; fixtures `RV-P8-pcrel-pair` (three records), `RV-P8-pcrel-pair-resolved` (linked arithmetic), `N17a`, `N17b`, `N17c`. |

## Decision procedure

1. Build the smallest experiment that distinguishes the options.
2. Record the measurement in `research/evidence/experiments/`.
3. Accept with an ADR if the decision changes an architecture boundary; otherwise
   mark the row `accepted` here with a one-line rationale.
4. Superseding an accepted row requires a new ADR reference in the same row.
