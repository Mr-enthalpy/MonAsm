# ADR-0040: The EVEX vector register is five bits, `xmm16`–`xmm31`

- Status: accepted
- Date: 2026-11-05
- Settles: `X86-P17` (the vector register at `xmm16`–`xmm31`) and the fifth
  register bit of `EC-06`/`EC-40`
- Supersedes: none
- Superseded by: none

## Context

`0.12.0` reaches `xmm0`–`xmm15` only. Every EVEX `xmm` slot is four bits: bit 3
at the inverted `R̄` (or `B̄` for `ModRM.rm`) and bits 2–0 in `ModRM`. AVX-512
defines thirty-two vector registers, and EVEX carries a second high bit, so the
question is whether that bit is usable for `movaps`/`vmovaps` and which prefix
bit carries it. `llvm-mc` 23.1.2 measures it on 2026-11-05 (`EXP-0042`):

| Source | Bytes | Length |
|---|---|---|
| `vmovaps %xmm16, %xmm0` | `62 b1 7c 08 28 c0` | 6 |
| `vmovaps %xmm0, %xmm16` | `62 e1 7c 08 28 c0` | 6 |
| `vmovaps %xmm24, %xmm24` | `62 01 7c 08 28 c0` | 6 |
| `vmovaps %xmm31, %xmm30` | `62 01 7c 08 28 f7` | 6 |
| `vmovaps %xmm30, %xmm31` | `62 01 7c 08 28 fe` | 6 |
| `vmovaps (%rax), %xmm16` | `62 e1 7c 08 28 00` | 6 |
| `vmovaps %xmm16, (%rax)` | `62 e1 7c 08 29 00` | 6 |
| `vmovaps (%r8), %xmm31` | `62 41 7c 08 28 38` | 6 |
| `vmovaps %xmm31, (%r8)` | `62 41 7c 08 29 38` | 6 |
| `vmovaps 2032(%rax), %xmm16` | `62 e1 7c 08 28 40 7f` | 7 |
| `vmovaps %xmm16, 2032(%rax)` | `62 e1 7c 08 29 40 7f` | 7 |
| `vmovaps -16(%rax), %xmm24` | `62 61 7c 08 28 40 ff` | 7 |
| `vmovaps %xmm24, -16(%rax)` | `62 61 7c 08 29 40 ff` | 7 |
| `vmovaps 8(%rax), %xmm31` | `62 61 7c 08 28 b8 08 00 00 00` | 10 |
| `vmovaps %xmm31, 8(%rax)` | `62 61 7c 08 29 b8 08 00 00 00` | 10 |
| `vmovaps 2056(%r8), %xmm16` | `62 c1 7c 08 28 80 08 08 00 00` | 10 |

Four facts decide the shape:

1. **`ModRM.reg` is five bits: bit 3 is `R̄` (P0 bit 7) and bit 4 is `R̄'`
   (P0 bit 4), both inverted.** `vmovaps %xmm16, %xmm0` has `P0 = b1`
   (`R̄ = 1`, `R̄' = 1`, so both destination bits are `0` and `reg = 0`) and
   `vmovaps %xmm0, %xmm16` has `P0 = e1` (`R̄' = 0`, so `reg = 16`).
   `vmovaps %xmm24, %xmm0` has `P0 = 91`: the destination's `R̄`/`R̄'` bits are
   both physical `1` (`reg = 0`) and the source's `X̄`/`B̄` bits are both
   physical `0` (`rm = 24`). `vmovaps %xmm30, %xmm31` keeps `P0 = 01` and adds
   `ModRM.reg = 7` (`62 01 7c 08 28 fe`), so the same prefix gives the
   destination-31 row and the source-31 row.
   Two failure modes are measured on the fourth row (`62 01 7c 08 28 f7` =
   `%xmm31, %xmm30`): writing the two bits raw instead of complemented gives
   `62 f1 7c 08 28 f7`, which `llvm-mc -disassemble` reads as `%xmm7, %xmm6`,
   and dropping the `R̄'` placement leaves the template bit set, giving
   `62 11 7c 08 28 f7` = `%xmm31, %xmm14`.
2. **`ModRM.rm` is five bits in register form: bit 3 is `B̄` and bit 4 is `X̄`
   (P0 bit 6), both inverted.** The same fourth row's `62 01 … f7` is
   `%xmm31, %xmm30`: `X̄` and `B̄` are both physical `0`, so `rm = 7` gains
   bits 4 and 3 and reads `31`, while `ModRM.reg = 6` reads `30`. Raising the
   physical `X̄` bit (`P0 = 41`) gives `62 41 7c 08 28 f7`, which decodes as
   `%xmm15, %xmm30` — the source loses bit 4 and drops from 31 to 15. The
   same prefix bit `X̄` extends a `SIB` index in a memory
   form (`EC-35`/`ADR-0035`), so its meaning is fixed by the form's `mod`,
   never inferred from an operand (`INV-05`).
3. **`X̄` is unused in the memory shapes.** With a memory operand every measured
   row keeps `X̄ = 1`, and `P0` carries only the base (`B̄`) and the register
   (`R̄`, `R̄'`). No `SIB` row exists under these opcodes, so `X̄` has nothing to
   extend there and its template value stays.
4. **Length does not change.** Every reachable register adds no byte: the six
   bytes of the register-direct and no-displacement rows, the seven of `disp8*16`
   and the ten of `disp32` are the same as their low-register twins. Legacy and
   VEX cannot reach `16` at all — `llvm-mc` rejects `movaps %xmm16, %xmm0` and
   selects EVEX for `vmovaps %xmm16, %xmm0` — so the widening is EVEX-only and
   needs no new row: the seven EVEX rows keep their templates and only their
   `xmm` slot widens.

## Decision

**`0.13.0` widens the `xmm` slot of the seven EVEX rows in place, from four bits
to five: bit 4 is `R̄'` for `ModRM.reg` and `X̄` for a register-direct
`ModRM.rm`. The form count stays at 74, and no legacy or VEX slot changes.**

1. **Six memory rows** (`xmm-base-disp8x16`, `xmm-base-disp32`,
   `base-disp8x16-xmm`, `base-disp32-xmm`, `xmm-base`, `base-xmm`). The `xmm`
   slot becomes `[12,1]` inverted (`R̄'`, bit 4) + `[15,1]` inverted (`R̄`, bit
   3) + `[43,3]`; the base rows are unchanged.
2. **The register-direct row** (`xmm-xmm`). The `dest` slot is
   `[12,1]` inverted + `[15,1]` inverted + `[43,3]`. The `src` slot, which is
   `ModRM.rm`, is `[14,1]` inverted (`X̄`, bit 4) + `[13,1]` inverted (`B̄`, bit
   3) + `[40,3]`.
3. **Nothing else widens.** A legacy or two-byte-VEX `xmm` slot stays at three
   bits and a three-byte-VEX slot at four, so `xmm16` on those forms is
   `E-OPERAND-004`, and `xmm32` is outside the five-bit field in every family.

The row, not the value, selects the family: a plan that names an EVEX row and
`xmm16` gets EVEX with `R̄' = 0`, and no path lets a legacy or VEX row emit
`16` by truncating it.

## Consequences

- `0.13.0` is a 74-form document with digest
  `sha256:79eabc2d19a7cf3cac84c857afd6a11b4f15063c7526f17f8782ace0b5ea3431`. Its positive fixture `X86-P17-sse-xmm16-31` is sixteen
  instructions and 112 bytes: the two register-direct directions at `16`, `24`,
  `30` and `31`, the no-displacement load/store at `%xmm16` and `%xmm31`, the
  compressed `disp8*16` content `127` and `-1`, and the promoted `disp32`.
- `N14m` pins `xmm16` on a `0.12.0` EVEX row (`field_bits = 4`, the version
  boundary), `N14n` pins `xmm32` on `0.13.0` (`field_bits = 5`), and `N14o` pins
  `xmm16` on a `0.13.0` VEX row (`field_bits = 4`, the family boundary).
- `EC-06` gains the fifth register bit and `EC-40` gains `R̄'`/`X̄` as the second
  inverted extension bit; no new `EC` row is needed.
- `07_definition_format.md` §8.1 gains the `0.13.0` digest row and the seven
  updated placement rows.
- Still absent: `ymm`/`zmm`, EVEX masking and broadcast, `movapd`'s `0x66` form,
  a `SIB` base or index under these opcodes, an SSE RIP-relative row, `mod = 00`
  for the GPR rows, the `0x67` prefix and 8/16-bit memory widths. `xmm16`–`xmm31`
  remain unreachable in legacy and VEX because those prefixes have no second
  extension bit at all.
