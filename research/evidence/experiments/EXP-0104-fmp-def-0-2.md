# EXP-0104 — the per-form extension requirement of `fmp-def/0.2`

- Date: 2026-11-08
- Question: which extension does a form need, and can this toolchain decide that
  by rejecting a plan that lacks it?
- Toolchain: `llvm-mc`/`llvm-objcopy` 23.1.2
- Definition source: `definitions/x86_64/0.68.0.json`, generated by
  `generate_0680.py` from `0.67.0.json` and checked by
  `tools/check_definition.py`
- Fixture oracle: `EXP-0045` (`P20.asm`, re-pinned by `X86-P74`)

Inputs: `probe.asm`
(`sha256:bed9d2a00c12d6416a73a57c04674acbad95b52b798e96a61300218ed2cd4260`,
69 bytes) and `evex-widths.s`
(`sha256:ad0037192ec3c392343824e83f76c95beb204104a5ed18db00debaeaaa1d37bc`,
90 bytes).

## 1. The width split, measured

`probe.asm` names one operation at three widths. `llvm-mc -show-encoding`:

| Source | Encoding | Family | Width field |
|---|---|---|---|
| `vmovaps %xmm1, %xmm0` | `c5 f8 28 c1` | VEX | `L = 0` (128-bit) |
| `vmovaps %ymm1, %ymm0` | `c5 fc 28 c1` | VEX | `L = 1` (256-bit) |
| `vmovaps %zmm1, %zmm0` | `62 f1 7c 48 28 c1` | EVEX | `L'L = 10` (512-bit) |

`bytes.txt` is the 14-byte `.text`
(`sha256:74655a06e96305986a57926d60e516f1ee38c2917141c1822f6c0684959c0663`),
`c5 f8 28 c1 c5 fc 28 c1 62 f1 7c 48 28 c1`.

The assembler always selects VEX for the 128- and 256-bit forms, so the
remaining EVEX width pairs are read with `llvm-mc -disassemble` on byte strings
it will not produce. `evex-widths.txt`
(`sha256:695adeda46b52a4927855ab6509ced06a847f7afc73f404a6a4e70d8117b33e6`):

| Bytes | Decodes as | `L'L` |
|---|---|---|
| `62 f1 7c 08 28 c1` | `vmovaps %xmm1, %xmm0` | `00` (128-bit) |
| `62 f1 7c 28 28 c1` | `vmovaps %ymm1, %ymm0` | `01` (256-bit) |
| `62 f1 7c 48 28 c1` | `vmovaps %zmm1, %zmm0` | `10` (512-bit) |

This repeats `EXP-0032` §1–§2's readings and is the same table `0.16.0` shipped
for the width rows. A row's requirement therefore tracks its widths, not its
mnemonic: two rows with the same mnemonic can need different extensions.

## 2. The toolchain has no gating oracle

`mattr.txt`
(`sha256:2107094af3837f13896d772be8af695bea10cc7a3bad2205650865a2226ccfa2`)
runs one instruction per case with the named extension switched off:

| Case | Flag | Result |
|---|---|---|
| `avx-off` | `-mattr=-avx` | rc 0, `c5 fc 28 c1` |
| `avx512f-off` | `-mattr=-avx512f` | rc 0, `62 f1 7c 48 28 c1` |
| `avx512vl-off` | `-mattr=-avx512vl` | rc 0, `c5 fc 28 c1` |
| `avx-all-off` | `-mattr=-avx,-avx512f,-avx512vl` | rc 0, `62 f1 7c 48 28 c1` |

`llvm-mc` 23.1.2 assembles a VEX or EVEX mnemonic regardless of `-mattr`, so
there is no local assembler that rejects a form for a missing extension. The
mapping from the width bits to extension names is `inference` from the
documented ISA dependency (VEX → AVX; EVEX 512-bit → AVX-512F; EVEX
128/256-bit → AVX-512VL), not a measured rejection. It is labelled that way in
`ADR-0103` and is the reason the fixture vectors test our gate, not the
assembler's.

## 3. The table

`generate_0680.py` adds the field to every form and asserts four things before
writing: the source is `0.67.0` in `fmp-def/0.1`, its renderer reproduces the
`0.67.0` forms block unchanged, each requirement is sorted and unique, and every
name appears in the table's own `enabled_extensions`. It prints:

```text
definitions/x86_64/0.68.0.json: 513 forms
  <baseline>                 388
  avx                        38
  avx,avx512f                29
  avx,avx512f,avx512vl       58
definition digest sha256:4c9ff304b305ceb831fd99e22bf0a7c422cce4104d08de604a6509f58e1501d2
```

The 29 `zmm` rows are exactly the rows with an `x86.zmm` slot; the 58 rows
carry `xmm` or `ymm` and no `zmm` slot. No `/legacy` or `/vex` row mixes widths,
so the classification is a function of the form set, not of a hand-written
list.

## 4. The fixtures

`fixture_p74.py` copies the 24 VEX instructions of `X86-P20` and changes only
the definition pin (`0.68.0` and the digest) and the plan's set (`["avx"]`). The
oracle is `EXP-0045/P20.asm` run again through `llvm-mc` + `llvm-objcopy`: 144
bytes, `input_sha256` and `output_sha256` identical to the `X86-P20` record.

`fixture_negatives_n06.py` writes two one-instruction plans:

| Fixture | Set | Row | Diagnostic |
|---|---|---|---|
| `N06b-per-form-extension-not-enabled` | `[]` | `x86:vmovaps/ymm-base/vex` | `E-TARGET-003`, `extension = avx` |
| `N06c-extension-not-declared-by-definition` | `["sse4.2"]` | `x86:movaps/xmm-xmm/legacy` | `E-TARGET-001`, `found = sse4.2` |

Both run through `cargo test -p fmp-cli --test fixtures`, which requires the
complete diagnostic set, and through `fmp materialize` by hand to confirm the
detail values quoted above.

## 5. Result

`X86-P74-per-form-requirements` emits 144 bytes from `0.68.0` with
`enabled_extensions: ["avx"]`; `N06b` and `N06c` are the first vectors for
`E-TARGET-003` and for the subset branch of `E-TARGET-001`. The `0.1` tables and
their equality fixtures are unchanged, and `0.68.0` has the same 513 form ids,
templates and slots as `0.67.0`, so no emitted byte moved.
