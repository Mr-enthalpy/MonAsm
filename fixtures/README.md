# Fixtures

Byte-exact test vectors. A fixture is only valid if it has an **independent**
oracle record. Generating `expected.bin` from our own materializer is forbidden
(`AGENTS.md` rule 5).

## Layout

```text
fixtures/<isa>/
  positive/
    <ID>-<slug>.fmp.json        frozen plan under test
    <ID>-<slug>.expected.bin    bytes from the oracle
    <ID>-<slug>.oracle.json     tool, version, exact command, sha256
  negative/
    N0X-<slug>.fmp.json         invalid plan
    N0X-<slug>.expected-error.json  { phase, errors: [{ code, path, detail_keys }] }
```

`<isa>` is `x86_64`, `aarch64`, or `rv64`.

## `phase`

`phase` says which stage must reject the plan, and defaults to `materialize`:

| Value | Meaning |
|---|---|
| `materialize` | The plan parses; `materialize()` must return exactly these diagnostics |
| `read` | `plan::read()` must reject the plan itself (a shape that is not in `fmp/0.1`), so there is no definition to look up |

`read` exists because the reader returns one diagnostic and stops. A plan that
hands the materializer a payload shape the schema does not have (`N15`'s
`{"mem": …}`) never reaches validation, and recording it as a `materialize`
fixture would assert the wrong stage. Any other value fails the gate.

## `oracle.json`

```json
{
  "tool": "llvm-mc",
  "version": "18.1.8",
  "command": "llvm-mc -triple=x86_64 -show-encoding ...",
  "input_sha256": "...",
  "output_sha256": "...",
  "notes": "manual check of 83 /0 ib vs 81 /0 id"
}
```

If the oracle is a manual derivation instead of a tool, say so explicitly and
record the reasoning under `research/evidence/experiments/`.

## Oracle provenance

`input_sha256` names the exact assembler input the record was made from: the
same bytes produce the same hash and nothing else does. The input is not copied
next to the fixture; when it was retained it lives under
`research/evidence/experiments/`. `python tools/oracle/rerun.py` resolves an
input by that hash, runs the pinned command, and compares the bytes with
`expected.bin` and `output_sha256`, so a record whose input is gone is reported
as `input-not-stored` instead of being trusted. A `kind` of
`manual+disassembly` states that the expected bytes are not the assembler output
(a hand-picked second encoding); the harness skips those.

## Rules

- Bytes are never generated by the code under test.
- `expected.bin` is binary; `.gitattributes` disables line-ending conversion.
- Each positive fixture maps to a vector ID in
  `docs/fmp-v0/06_validation_matrix.md`.
- Each negative fixture maps to a registry code in `docs/fmp-v0/04_errors.md`.
- A fixture that is excluded from v0 needs a rejection fixture so the exclusion
  cannot be mistaken for support.
